# План по созданию расширенного дашборда на GitHub Pages

Этот документ описывает шаги по реализации многофункционального сайта для отображения результатов CI/CD.

## Фаза 1: Создание версионированных страниц для каждой сборки

**Цель:** Каждая сборка должна публиковаться по уникальному URL, чтобы сохранять историю и иметь постоянные ссылки на отчеты.

1.  **Модификация `ci-flow.yml`:**
    *   Передавать в `deploy-github-pages.yml` не только номер сборки, но и имя ветки.
    *   **Действие:** Добавить `github.ref_name` в секцию `with` при вызове `deploy_reports`.

2.  **Модификация `deploy-github-pages.yml`:**
    *   Принимать `build_number` и `branch_name` как входные параметры (`inputs`).
    *   **Действие:** Добавить `inputs` в секцию `on.workflow_call`.
    *   Создавать директорию для сайта по шаблону `.site/<branch_name>/<build_number>`. Имя ветки нужно "санитизировать" (например, заменять `/` на `-`), чтобы избежать проблем с путями.
    *   **Действие:** Изменить шаг `Assemble Site Structure`, чтобы он создавал и наполнял версионную директорию.

3.  **Создание шаблона для страницы сборки:**
    *   Создать новый HTML-файл (`.source/_layouts/build.html`), который будет служить шаблоном для страницы каждой сборки.
    *   **Структура шаблона:**
        *   `<header>`: Место для статистики и ссылок.
        *   `<iframe>`: Для встраивания Allure-отчета (`src="reports/allure/index.html"`).
    *   **Действие:** В `deploy-github-pages.yml` создать Markdown-файл для Jekyll (например, `.site/<branch_name>/<build_number>/index.md`), который будет использовать этот шаблон.

## Фаза 2: Динамическая главная страница (`index.html`)

**Цель:** Создать "живую" главную страницу, которая будет отображать список всех доступных сборок.

1.  **Сбор данных о сборках:**
    *   На каждом запуске `deploy-github-pages.yml` нужно генерировать небольшой JSON-файл с метаданными о текущей сборке (`build_number`, `branch_name`, `status`, `timestamp`).
    *   **Действие:** Добавить шаг, создающий `build-meta.json` и сохраняющий его в артефактах сборки.

2.  **Агрегация данных:**
    *   На главной странице (`.site/index.html`) разместить JavaScript-код.
    *   Этот скрипт будет:
        *   Загружать "индексный" файл (например, `builds-manifest.json`), который содержит список всех `build-meta.json`.
        *   На каждом деплое нужно будет скачивать старый `builds-manifest.json` с `gh-pages`, добавлять в него новую запись и загружать обратно.
        *   **Действие:** Реализовать логику обновления манифеста в `deploy-github-pages.yml`.

3.  **Отрисовка интерфейса:**
    *   JavaScript на главной странице будет динамически генерировать HTML на основе загруженного `builds-manifest.json`, создавая список сборок с группировкой по веткам.

## Фаза 3: Обогащение страниц данными

**Цель:** Наполнить страницы статистикой и полезной информацией.

1.  **Сбор статистики:**
    *   В workflow `unit-tests.yml` и `static-analysis.yml` после выполнения тестов и линтеров нужно парсить отчеты (`.xcresult`, `swiftlint-report.json`) для извлечения ключевых метрик (количество упавших тестов, найденных ошибок).
    *   **Действие:** Добавить шаги с `jq` (для JSON) или другими утилитами для парсинга. Сохранять метрики в файл (например, `build-stats.json`) и передавать в артефактах.

2.  **Отображение статистики:**
    *   На шаге `deploy-github-pages.yml` читать `build-stats.json`.
    *   **Действие:** Передавать эти данные в Jekyll через `_data` файлы или напрямую вставлять в HTML-шаблон страницы сборки. Это позволит отобразить статистику в `<header>`.

## Фаза 4: Будущие улучшения

*   **Интерактивность:** Добавить фильтры и сортировку на главной странице с помощью JavaScript.
*   **API GitHub:** Использовать GitHub API для получения статусов сборок в реальном времени или для реализации функции "перезапуска".
*   **Визуализация:** Добавить графики (например, с помощью Chart.js) для отображения трендов по `main` ветке.
