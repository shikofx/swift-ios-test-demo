= Новые требования к дашборду отчетов на GitHub Pages

Цель: Модифицировать существующие макеты Jekyll (`swift-dashboard.html`) для создания динамического дашборда. Отображение контента будет управляться параметрами из `Front Matter`, а сами списки (билдов, веток) будут передаваться как данные.

== Существующая структура

Уже существуют макеты Jekyll, которые определяют общий вид страниц:
*   `swift-dashboard.html`: Основной макет для страниц отчетов, включающий хедер с навигацией по типам отчетов (Allure, SwiftLint и т.д.) и футер с информацией о билде.

Наша задача — доработать эти макеты, добавив в них условные блоки для отображения списков, и научиться передавать в них данные из CI.

== Сценарии отображения контента (управляются через `Front Matter`)

Для управления логикой отображения вводится новый параметр в `Front Matter`: `is_main_branch` (тип `boolean`).

=== 1. Главная страница (`is_main_branch: true`)

*   **URL:** `https://<user>.github.io/<repo>/`
*   **Генерируемый файл:** `index.md` (в CI).
*   **Макет Jekyll:** `swift-dashboard.html`.
*   **Логика макета:** Если `page.is_main_branch` равно `true`, то в контентной области отображаются **два блока**:
    1.  **Блок "Билды ветки `main`"**: Прокручиваемый список билдов для `main`.
        Если билдов нет, отображается "No builds yet".
    2.  **Блок "Актуальные ветки"**: Прокручиваемый список всех существующих веток (кроме `main`).
        Если других веток нет, отображается "No branches yet".
*   **Данные для списков:** Списки будут передаваться через `Front Matter` (например, `page.main_builds` и `page.actual_branches`).

=== 2. Страница ветки (`is_main_branch: false`)

*   **URL:** `https://<user>.github.io/<repo>/<sanitized_branch_name>/<build_number>/`
*   **Генерируемый файл:** `/<sanitized_branch_name>/<build_number>/index.md` (в CI).
*   **Макет Jekyll:** `swift-dashboard.html`
*   **Логика макета:** Если `page.is_main_branch` равно `false`, то в контентной области отображается **один блок** на всю доступную высоту:
    1.  **Блок "Билды ветки `<branch_name>`"**: Прокручиваемый список всех билдов для текущей ветки.
    2.  Над блоком должна быть навигационная ссылка `<< Back to main`.
    *   Если билдов для ветки нет, вместо списка отображается "No builds yet".
*   **Данные для списка:** Список билдов будет передаваться через `Front Matter` (например, `page.branch_builds`).

== Общие требования к реализации

*   **Шаблонизация:** Вся логика отображения блоков (два блока vs один блок) должна быть реализована внутри макетов Jekyll с использованием условных операторов Liquid (`{% if page.is_main_branch %}`).
*   **Генерация данных:** CI-пайплайн отвечает за:
    *   Создание структуры папок (`/<branch>/<build>`).
    *   Сбор метаданных о билдах и ветках.
    *   Генерацию `.md` файлов с `Front Matter`, который содержит флаг `is_main_branch` и данные для списков.

== План разработки

=== Этап 1: Отладка условного отображения блоков в макете

**Цель:** Проверить, что макет `swift-dashboard.html` может корректно отображать либо один, либо два блока в зависимости от флага `is_main_branch`, используя *фейковые данные* и **не меняя текущую структуру сайта**.

1.  **Модифицировать макет `swift-dashboard.html`**:
    *   Добавить условную логику `{% if page.is_main_branch %}`.
    *   Внутри `if` разместить HTML-разметку для двух блоков ("Билды ветки main", "Актуальные ветки") с *фейковыми* статичными списками.
    *   Внутри `else` разместить HTML-разметку для одного блока ("Билды ветки ...") с *фейковым* статичным списком и ссылкой `<< Back to main`.
2.  **Обновить CI (`build_site`) для тестирования**:
    *   Модифицировать существующий шаг генерации `index.md` в `ci-flow.yml`.
    *   Добавить в `Front Matter` генерируемого `index.md` флаг `is_main_branch`.
    *   Если текущая ветка `main`, устанавливать `is_main_branch: true`.
    *   Если любая другая ветка, устанавливать `is_main_branch: false`.
    *   **Важно:** На этом этапе мы *не создаем* новую структуру папок. Мы просто меняем содержимое единственного `index.md`, который перезаписывается при каждом билде.

**Результат этапа:** При запуске CI на ветке `main` на сайте отображаются два блока с фейковыми данными. При запуске на любой другой ветке — один блок с фейковыми данными.

=== Этап 2: Поэтапное формирование структуры сайта

**Цель:** Аккуратно перейти от одностраничного сайта к многоуровневой структуре `/<branch>/<build>`, не ломая существующую функциональность.

1.  **Шаг 2.1: Создание структуры папок.** Модифицировать `build_site` для создания папок `_site/<sanitized_branch_name>/<build_number>` и перемещения туда "сырых" отчетов (Allure, SwiftLint и т.д.).
2.  **Шаг 2.2: Генерация страницы билда.** Научить CI создавать `index.md` *внутри* папки билда (`/<branch>/<build>/index.md`) с флагом `is_main_branch: false`.
3.  **Шаг 2.3: Генерация главной страницы.** Научить CI создавать `index.md` *в корне* сайта (`/index.md`) с флагом `is_main_branch: true`.

**Результат этапа:** Сайт имеет правильную структуру URL. Главная страница всегда показывает два блока, а страницы билдов — один. Данные все еще фейковые.

=== Этап 3: Динамическое наполнение данными

**Цель:** Заменить фейковые данные в шаблонах на реальные, собранные во время CI.

1.  **Сбор метаданных в CI**: Реализовать логику сбора информации о билдах и ветках (например, сканируя `gh-pages` ветку).
2.  **Передача данных через Front Matter**: Модифицировать CI так, чтобы он формировал списки (в формате YAML) и передавал их в `Front Matter` генерируемых `.md` файлов (например, `page.main_builds`, `page.actual_branches`).
3.  **Обновление макета**: Заменить фейковые данные в макете `swift-dashboard.html` на циклы Liquid (`{% for ... %}`), которые будут итерироваться по данным, полученным из `Front Matter`.
