= План создания CI-дашборда (Архитектура "Динамического обнаружения")

Цель: Создать интерактивный дашборд, который динамически генерирует свое содержимое, сканируя структуру папок и файлов в репозитории `shikofx/github-pages`. Этот подход отменяет необходимость в поддержке единого файла-манифеста, делая систему более надежной и простой.

== Архитектура хранения данных

Структура в репозитории `shikofx/github-pages` является источником правды для дашборда.

```
.
├── swift-ios-test-demo/      # Папка проекта
│   ├── main/                 # Папка для ветки main
│   │   ├── branch-info.json  # Метаданные ветки
│   │   └── 25/               # Папка для запуска №25
│   │       ├── build-meta.json # Метаданные билда
│   │       └── reports/      # Папка с отчетами (Allure, Coverage и т.д.)
│   └── feature-new-login/    # Папка для другой ветки
│       ├── branch-info.json  # Метаданные ветки для хранения оригинального имени
│       └── 28/               # Папка для запуска №28
│           ├── build-meta.json
│           └── reports/
└── ...                       # Другие проекты
```

---

== Этап 1: Публикация "сырых" данных билда в `build_site`

Цель: Модифицировать существующий `job` `build_site` в файле `ci-flow.yml` для публикации отчетов и метаданных каждого билда в репозиторий `shikofx/github-pages`.

1.  **Модификация `job` `build_site` (`swift-ios-test-demo`):**
    *   **Шаг 1: Скачивание артефактов**. Этот шаг уже существует и скачивает все отчеты.
    *   **Шаг 2: Checkout репозитория `github-pages`**. Добавить шаг, который использует `actions/checkout` с токеном или SSH-ключом для клонирования `shikofx/github-pages` в отдельную папку (например, `gh-pages-repo`).
    *   **Шаг 3: Создание структуры и метаданных**. Добавить шаг со скриптом, который:
        *   Создает путь внутри `gh-pages-repo`: `swift-ios-test-demo/<sanitized_branch_name>/<run_number>/`.
        *   Создает файл `build-meta.json` с информацией о билде (номер, хэш, статус, дата, ссылки на отчеты).
        *   Проверяет наличие `branch-info.json` в папке ветки и создает его, если это первый запуск.
        *   Перемещает скачанные артефакты с отчетами в подпапку `reports/`.
    *   **Шаг 4: Commit & Push**. Добавить шаг, который выполняет `git commit` и `git push` для папки `gh-pages-repo`, отправляя изменения в репозиторий `github-pages`.

**Результат этапа:** Репозиторий `github-pages` наполняется данными о билдах. Каждый запуск CI атомарно добавляет свою папку, не затрагивая другие. Существующая логика сборки сайта Jekyll в `build_site` пока остается без изменений.
---

== Этап 2: Генерация данных для Jekyll

Цель: Создать скрипт, который будет запускаться *перед* сборкой Jekyll, сканировать структуру папок в `github-pages` и генерировать на лету `_data` файлы, которые Jekyll сможет использовать.

1.  **Создание скрипта-агрегатора (`pre-build.sh` или `pre-build.py`):**
    *   Этот скрипт будет находиться в репозитории `github-pages`.
    *   **Логика скрипта:**
        1.  Сканирует директорию `swift-ios-test-demo/`.
        2.  Находит все папки-ветки.
        3.  Для каждой ветки находит все папки-билды.
        4.  Читает `build-meta.json` из каждого билда.
        5.  Формирует единый `builds.json` и сохраняет его в `_data/builds.json`. Этот файл будет содержать массив всех билдов, сгруппированных по веткам.
2.  **Интеграция в CI (`github-pages`):**
    *   В workflow сборки Jekyll-сайта (в репозитории `github-pages`) добавить шаг, который запускает этот скрипт *перед* шагом `actions/jekyll-build-pages`.

**Результат этапа:** Перед каждой сборкой сайта Jekyll получает актуальный файл `_data/builds.json`, который описывает всё состояние CI.
---

== Этап 3: Создание страниц дашборда

Цель: Создать Jekyll-шаблоны, которые используют данные из `_data/builds.json` для отображения информации.

1.  **Главная страница (`index.md`):**
    *   Использует макет `swift-dashboard.html`.
    *   С помощью логики Liquid (`{% for ... %}`) и `site.data.builds` отображает:
        *   Список билдов для ветки `main`.
        *   Список всех остальных веток.
2.  **Страницы веток:**
    *   Использовать плагин `jekyll-archives` или аналогичный для автоматической генерации страниц для каждой ветки (например, по URL `/branches/<branch_name>/`).
    *   Шаблон для этих страниц будет фильтровать `site.data.builds` и показывать только билды, относящиеся к текущей ветке.
3.  **Страницы билдов:**
    *   Для каждого билда будет создаваться страница (например, `/builds/<branch_name>/<build_number>/`).
    *   Эта страница будет содержать `iframe` для Allure-отчета и ссылки на другие отчеты (SwiftLint, Coverage), которые лежат в папке `reports/`.

**Результат этапа:** Полноценный сайт-дашборд. Главная страница показывает сводку. С нее можно перейти на страницу ветки, а оттуда — на страницу конкретного билда с отчетами.
---

== Этап 4: Финализация и история Allure

Цель: Обеспечить корректное отображение истории в Allure.

1.  **Настройка истории Allure:**
    *   В `job` `generate_allure_report` (или в `build_site`) перед генерацией Allure-отчета добавить шаг, который:
        1.  Клонирует репозиторий `github-pages`.
        2.  Находит папку последнего билда для *текущей* ветки.
        3.  Копирует из нее директорию `reports/allure/history`.
    *   Использовать эту папку при генерации нового отчета.

**Результат этапа:** Отчеты Allure для каждой ветки содержат исторические данные и графики трендов.
