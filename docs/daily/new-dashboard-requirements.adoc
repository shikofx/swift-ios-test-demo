= Новые требования к дашборду отчетов на GitHub Pages

Цель: Модифицировать существующие макеты Jekyll (`swift-dashboard.html`) для создания динамического дашборда. Отображение контента будет управляться параметрами из `Front Matter`, а сами списки (билдов, веток) будут передаваться как данные.

== Существующая структура

Уже существуют макеты Jekyll, которые определяют общий вид страниц:
*   `swift-dashboard.html`: Основной макет для страниц отчетов, включающий хедер с навигацией по типам отчетов (Allure, SwiftLint и т.д.) и футер с информацией о билде.

Наша задача — доработать эти макеты, добавив в них условные блоки для отображения списков, и научиться передавать в них данные из CI.

== Сценарии отображения контента (управляются через `Front Matter`)

Для управления логикой отображения вводится новый параметр в `Front Matter`: `is_main_branch` (тип `boolean`).

=== 1. Главная страница (`is_main_branch: true`)

*   **URL:** `https://<user>.github.io/<repo>/`
*   **Генерируемый файл:** `index.md` (в CI).
*   **Макет Jekyll:** `swift-dashboard.html`.
*   **Логика макета:** Если `page.is_main_branch` равно `true`, то **в хедере, после меню навигации,** отображаются **два блока**:
    1.  **Блок "Билды ветки `main`"**: Прокручиваемый список билдов для `main`.
        Если билдов нет, отображается "No builds yet".
    2.  **Блок "Актуальные ветки"**: Прокручиваемый список всех существующих веток (кроме `main`).
        Если других веток нет, отображается "No branches yet".
*   **Данные для списков:** Списки будут передаваться через `Front Matter` (например, `page.main_builds` и `page.actual_branches`).

=== 2. Страница ветки (`is_main_branch: false`)

*   **URL:** `https://<user>.github.io/<repo>/<sanitized_branch_name>/<build_number>/`
*   **Генерируемый файл:** `/<sanitized_branch_name>/<build_number>/index.md` (в CI).
*   **Макет Jekyll:** `swift-dashboard.html`
*   **Логика макета:** Если `page.is_main_branch` равно `false`, то **в хедере, после меню навигации,** отображается **один блок** на всю доступную высоту:
    1.  **Блок "Билды ветки `<branch_name>`"**: Прокручиваемый список всех билдов для текущей ветки.
    2.  Над блоком должна быть навигационная ссылка `<< Back to main`.
    *   Если билдов для ветки нет, вместо списка отображается "No builds yet".
*   **Данные для списка:** Список билдов будет передаваться через `Front Matter` (например, `page.branch_builds`).

== План разработки

=== Этап 1: Отладка отображения блоков с фейковыми данными
**Цель:** Проверить, что макеты (`swift-dashboard.html`, `swift-allure-main-page.html`) могут корректно отображать либо один, либо два блока в зависимости от флага `is_main_branch`, используя *фейковые данные* и **не меняя текущую структуру сайта**.

1.  **Модифицировать макеты**:
    *   Добавить условную логику `{% if page.is_main_branch %}`.
    *   Внутри `if` разместить HTML-разметку для двух блоков с *фейковыми* статичными списками **внутри тега `<header>`**.
    *   Внутри `else` разместить HTML-разметку для одного блока с *фейковым* статичным списком и ссылкой `<< Back to main` **внутри тега `<header>`**.
2.  **Обновить CI (`build_site`) для тестирования**:
    *   Модифицировать существующий шаг генерации `index.md` в `ci-flow.yml`.
    *   Добавить в `Front Matter` генерируемого `index.md` флаг `is_main_branch` в зависимости от того, является ли текущая ветка `main`.
    *   **Важно:** На этом этапе мы *не создаем* новую структуру папок. Мы просто меняем содержимое единственного `index.md`, который перезаписывается при каждом билде.

**Результат этапа:** При запуске CI на ветке `main` на сайте отображаются два блока с фейковыми данными. При запуске на любой другой ветке — один блок.

=== Этап 2: Формирование и передача реальных данных

**Цель:** Заменить фейковые данные в шаблонах на реальные, собранные во время CI, **продолжая работать с одностраничной структурой**.

1.  **Сбор метаданных в CI**: Реализовать логику сбора информации о билдах и ветках (например, сканируя `gh-pages` ветку или используя API GitHub).
2.  **Передача данных через Front Matter**: Модифицировать CI так, чтобы он формировал списки (в формате YAML) и передавал их в `Front Matter` генерируемых `.md` файлов (например, `page.main_builds`, `page.actual_branches`).
3.  **Обновление макета**: Заменить фейковые данные в макетах на циклы Liquid (`{% for ... %}`) и добавить логику для отображения "No builds yet" / "No branches yet", если списки пусты.

**Результат этапа:** Сайт показывает 1 или 2 блока с *реальными* данными, собранными в CI.

=== Этап 3: Формирование структуры сайта

**Цель:** Аккуратно перейти от одностраничного сайта к многоуровневой структуре `/<branch>/<build>`, используя уже отлаженную логику отображения и наполнения данными.

1.  **Создание структуры папок:** Модифицировать `build_site` для создания папок `_site/<sanitized_branch_name>/<build_number>` и перемещения туда "сырых" отчетов (Allure, SwiftLint и т.д.).
2.  **Генерация страниц билдов:** Научить CI создавать `index.md` *внутри* папок билдов (`/<branch>/<build>/index.md`) с флагом `is_main_branch: false` и передавать туда данные о билдах этой ветки.
3.  **Генерация главной страницы:** Научить CI создавать `index.md` *в корне* сайта (`/index.md`) с флагом `is_main_branch: true` и передавать туда данные о билдах `main` и других ветках.

**Результат этапа:** Сайт имеет правильную структуру URL. Главная страница всегда показывает два блока с реальными данными, а страницы билдов — один блок с реальными данными.

=== Этап 4: Настройка истории Allure

**Цель:** Научить Allure подхватывать историю тестов для каждой ветки отдельно.

1.  **Модифицировать CI:** Перед генерацией нового Allure-отчета для билда, реализовать логику поиска и скачивания папки `history` из Allure-отчета *предыдущего* билда **этой же ветки**.
2.  **Использовать историю:** Передать скачанную папку `history` в команду генерации нового отчета.

**Результат этапа:** Отчеты Allure для каждой ветки содержат исторические данные и графики трендов.
