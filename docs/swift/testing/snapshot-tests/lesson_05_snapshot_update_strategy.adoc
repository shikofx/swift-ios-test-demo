Мы научились писать и автоматически проверять Snapshot-тесты. Но что делать, когда UI меняется намеренно и эталонные снимки нужно обновить? Если делать это хаотично, можно случайно "узаконить" баг. В этом уроке мы рассмотрим надежную стратегию обновления эталонов при работе в команде.

== 1. Проблема: как ревьюить изменения в снимках?

Эталонные снимки — это бинарные файлы (изображения). В отличие от кода, Git не может показать осмысленный `diff` для них. Когда вы видите в Pull Request'е, что файл `LoginViewController.png` изменился, у вас возникает вопрос:

*   Это изменение — ожидаемый результат новой фичи?
*   Или это случайная визуальная регрессия, которую разработчик не заметил?

Просто доверять тому, что разработчик обновил снимок, — опасно. Нужен прозрачный процесс.

== 2. Золотое правило

[quote]
Разработчик, который внес **намеренные** изменения в UI, несет ответственность за обновление соответствующих эталонных снимков.

== 3. Командный воркфлоу обновления эталонов

Вот пошаговый процесс, который позволяет безопасно обновлять эталоны.

=== Шаг 1: Разработчик вносит изменения в UI

Разработчик реализует новую фичу или исправляет баг, который меняет внешний вид компонента.

=== Шаг 2: Локальный запуск тестов и их падение

Разработчик запускает Snapshot-тесты у себя на компьютере. Тесты, естественно, падают, потому что новый UI не совпадает со старыми эталонами.

=== Шаг 3: Локальная перезапись эталонов

Убедившись, что новый UI выглядит корректно, разработчик временно устанавливает `isRecording = true` для упавших тестов и запускает их снова. Это перезаписывает старые эталонные `.png` файлы новыми.

=== Шаг 4: Атомарный коммит

Это **самый важный шаг**. Разработчик должен сделать коммит, который содержит **и код, и измененные файлы снимков (`.png`) вместе**. Нельзя разделять эти изменения на разные коммиты.

[source,bash]
--
# Пример коммита
git add LoginViewController.swift LoginViewController.png
git commit -m "feat: Add subtitle to login screen"
--

=== Шаг 5: Создание и ревью Pull Request (PR)

Разработчик создает Pull Request. Теперь наступает очередь ревьюера.

Задача ревьюера — не просто прочитать код, а **внимательно изучить изменения в файлах-снимках**. Современные платформы, такие как GitHub, GitLab или Bitbucket, отлично показывают diff для изображений.

*   **2-up View:** Показывает старое и новое изображение рядом.
*   **Swipe View:** Позволяет двигать ползунок, чтобы сравнить "до" и "после".
*   **Onion Skin View:** Накладывает одно изображение на другое с прозрачностью.

Ревьюер должен визуально подтвердить, что изменения на снимке соответствуют описанию задачи. Если да — PR одобряется. Если на снимке есть что-то неожиданное (например, поехала верстка другого элемента) — PR отклоняется. **Именно так Snapshot-тесты ловят регрессии на этапе код-ревью.**

=== Шаг 6: CI проверяет консистентность

После создания PR запускается CI. Его задача — убедиться, что снимки, которые разработчик сгенерировал у себя локально, пиксель в пиксель совпадают со снимками, сгенерированными в чистом окружении CI. Если этот шаг падает, это сигнал о рассинхронизации окружений (например, разные версии ОС или Xcode).

== 4. Лучшие практики

*   **Четкие описания PR:** Всегда указывайте в описании Pull Request'а, что были обновлены Snapshot-тесты. Это сигнал для ревьюеров быть особенно внимательными.
*   **Не обновляйте вслепую:** Никогда не перезаписывайте эталоны, не убедившись визуально, что новый вид компонента корректен.
*   **Изолируйте изменения:** Старайтесь, чтобы один PR содержал логически связанные изменения. Не стоит в одном PR менять и логику, и цвет кнопок по всему приложению.
