В предыдущих уроках мы подготовили проект и разобрали структуру тестовых классов. Теперь настало время написать наш первый осмысленный UI-тест. Мы автоматизируем сценарий успешного входа в приложение.

== Тестовый сценарий: Успешный логин

Наш первый тест будет проверять самый базовый сценарий:

1.  Запустить приложение.
2.  Ввести валидное имя пользователя (`standard_user`).
3.  Ввести валидный пароль (`secret_sauce`).
4.  Нажать на кнопку "Login".
5.  Убедиться, что произошел переход на экран каталога продуктов.

== Поиск элементов: Accessibility Inspector

Чтобы взаимодействовать с элементом (нажать на него или ввести текст), тест должен его сначала найти. `XCUITest` находит элементы, используя их *свойства доступности* (Accessibility).

Лучший инструмент для исследования этих свойств — **Accessibility Inspector**.

.  Запустите его из Xcode: `Xcode` -> `Open Developer Tool` -> `Accessibility Inspector`.
.  В окне инспектора выберите ваш симулятор или устройство.
.  Нажмите на иконку "прицела" (Start inspection) и наведите курсор на любой элемент в приложении.

Инспектор покажет вам всю информацию об элементе: его тип (`Button`, `Text Field`), заголовок (`Label`) и, самое главное, **идентификатор** (`Identifier`).

=== Программный способ: Печать дерева элементов

Иногда удобнее увидеть всю иерархию элементов экрана в виде текста. Это можно сделать прямо во время выполнения теста.

.  Поставьте точку останова (breakpoint) в вашем тесте после запуска приложения (`app.launch()`).
.  Запустите тест в режиме отладки.
.  Когда выполнение остановится на брейкпоинте, в консоли отладки (lldb) введите команду `po app` или `print(app.debugDescription)`.

Вы получите в консоли полное дерево всех элементов, видимых на экране в данный момент.

[source, text]
--

  Window, 0x600002c1c1c0, {{0.0, 0.0}, {390.0, 844.0}}

=== Стратегии поиска элементов

Существует несколько способов найти элемент:

*   **По Accessibility Identifier (Предпочтительный способ):** Это уникальный идентификатор, который разработчик задает специально для тестов. Он не зависит от текста на элементе и локализации. Это самый стабильный и надежный способ.
*   **По тексту (`.staticTexts["Products"]`, `.buttons["Login"]`):** Можно искать элемент по видимому тексту. Этот способ хрупкий, так как текст может измениться или быть переведен на другой язык.
*   **По типу и индексу (`.textFields.element(boundBy: 0)`):** Поиск элемента по его порядковому номеру на экране. Это самый хрупкий способ, который следует избегать, так как порядок элементов может легко измениться.

[TIP]
====
Поиск по тексту — хороший компромисс, когда у элемента нет `accessibilityIdentifier`.
====

=== Что делать, если у элемента нет идентификатора?

Это частая ситуация. У вас есть два пути, и выбор зависит от того, есть ли у вас доступ к исходному коду приложения.

==== Вариант 1: Добавить идентификатор в код (Предпочтительный)

Если у вас есть доступ к коду, **всегда** старайтесь добавить `accessibilityIdentifier`. Это самый надежный и поддерживаемый способ.

*   **Через Storyboard:**
    1.  Откройте нужный Storyboard-файл.
    2.  Выберите элемент (например, `UITextField`).
    3.  Откройте **Identity Inspector** (Инспектор идентификации) на правой панели Xcode.
    4.  В разделе **Accessibility** введите уникальное имя в поле **Identifier**.

*   **Программно в коде:**
    В методе `viewDidLoad` вашего `UIViewController` добавьте строку:
    [source, swift]
    --
    // Найти кнопку по тексту, который видит пользователь
    let loginButton = app.buttons["Login"]
    --

    Главный недостаток — если текст изменится (например, "Login" на "Sign In") или будет переведен на другой язык, тест сломается.
    ====
*   **По типу и индексу (`.textFields.element(boundBy: 0)`):** Поиск элемента по его порядковому номеру на экране. Это самый хрупкий способ, который следует избегать, так как порядок элементов может легко измениться.

== Пишем код теста

Откроем наш основной тестовый файл `SDET Demo AppUITests/SDET_Demo_AppUITests.swift` и изменим метод `testExample()`.

.  **Переименуем тест:** Дадим ему осмысленное имя `testSuccessfulLogin`.
.  **Напишем шаги сценария:**

[source, swift]
--
import XCTest

final class SDET_Demo_AppUITests: XCTestCase {

    // ... методы setUpWithError и tearDownWithError остаются без изменений ...

    @MainActor
    func testSuccessfulLogin() throws {
        // 1. Инициализируем приложение
        let app = XCUIApplication()
        app.launch()

        // 2. Находим элементы по их accessibilityIdentifier
        let usernameTextField = app.textFields["Username input"]
        let passwordTextField = app.secureTextFields["Password input"]
        let loginButton = app.buttons["Login button"]

        // 3. Взаимодействуем с элементами
        usernameTextField.tap()
        usernameTextField.typeText("standard_user")

        passwordTextField.tap()
        passwordTextField.typeText("secret_sauce")

        loginButton.tap()

        // 4. Проверяем результат (ассерт)
        // После успешного входа мы должны увидеть заголовок "Products" на экране каталога.
        let productsHeader = app.staticTexts["Products"]

        // Убедимся, что заголовок появился на экране в течение 5 секунд.
        // Использование ожидания (waitForExistence) — хорошая практика в UI-тестах.
        XCTAssertTrue(productsHeader.waitForExistence(timeout: 5))
    }

    // ... тест testLaunchPerformance можно пока оставить или удалить ...
}
--

=== Проблема: Элемент перекрыт клавиатурой

Очень часто после ввода текста с помощью `.typeText()` на экране остается клавиатура, которая может перекрывать кнопку, которую вы хотите нажать следующей. Тест упадет с ошибкой "UI element is not hittable".

Чтобы решить эту проблему, клавиатуру нужно скрыть. Вот самые популярные способы:

*   **Нажать кнопку "Return" на клавиатуре:** Это самый надежный способ, имитирующий нажатие пользователем клавиши "Ввод".
[source, swift]
--
// После ввода текста в последнее поле
app.keyboards.buttons["Return"].tap()
--

*   **Нажать на другой элемент:** Можно тапнуть по любому статичному элементу вне поля ввода, например, по заголовку.
[source, swift]
--
app.staticTexts["Products"].tap()
--

[IMPORTANT]
====
*UI-тест нашел баг!*

В нашем приложении `SDET Demo App` существует баг: после ввода данных в поля логина и пароля клавиатура не скрывается ни одним из стандартных способов. Кнопка "Return" на ней отсутствует, а тап по другим элементам не приводит к ее скрытию.

Из-за этого наш тест `testSuccessfulLogin` будет падать с ошибкой `UI element is not hittable` при попытке нажать на кнопку "Login", так как она физически перекрыта клавиатурой.

Это отличный пример того, как UI-тесты помогают находить не только функциональные, но и важные UI/UX баги. В рамках нашего курса мы будем считать, что этот тест **падает по уважительной причине** до тех пор, пока баг в приложении не будет исправлен. Наша задача как автоматизаторов — зарепортить этот баг команде разработки.
====

=== Разбор кода

*   `app.textFields["Username input"]`: Мы обращаемся к коллекции всех текстовых полей (`textFields`) и просим найти то, у которого `accessibilityIdentifier` равен `"Username input"`.
*   `app.secureTextFields`: Поля для ввода пароля имеют отдельный тип `secureTextFields`.
*   `.tap()`: Имитирует простое нажатие на элемент.
*   `.typeText("...")`: Имитирует ввод текста с клавиатуры.
*   `XCTAssertTrue(...)`: Это утверждение (assertion) из фреймворка `XCTest`. Тест будет считаться успешным, только если условие внутри `XCTAssertTrue` истинно.
*   `.waitForExistence(timeout: 5)`: Это важный метод. Он говорит тесту подождать появления элемента на экране в течение указанного времени (в данном случае, 5 секунд). UI не всегда обновляется мгновенно, поэтому ожидания делают тесты более стабильными. Если элемент не появится за это время, тест упадет.

== Запуск теста

Вы можете запустить только что написанный тест, нажав на иконку ромбика слева от имени функции `testSuccessfulLogin` в Xcode.

Вы увидите, как симулятор запустится, и тест автоматически выполнит все шаги, которые мы запрограммировали. Если все сделано правильно, ромбик станет зеленой галочкой.

Поздравляю, вы написали и запустили свой первый полноценный UI-тест!
