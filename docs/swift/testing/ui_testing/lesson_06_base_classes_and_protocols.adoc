= Создание базовых классов и протоколов для Page Objects

В предыдущем уроке мы успешно применили паттерн Page Object Model. Наши тесты стали гораздо чище, но внутри самих Page Object'ов все еще есть проблемы:

*   **Дублирование кода:** Каждый Page Object хранит свойство `app` и имеет одинаковый инициализатор `init(app: XCUIApplication)`.
*   **"Магические строки":** Идентификаторы элементов, такие как `"More-tab-item"` или `"Login"`, разбросаны по коду. Если идентификатор изменится, его придется исправлять в нескольких местах.
*   **Повторяющиеся действия:** Мы часто будем выполнять одинаковые последовательности действий, например, "подождать появления элемента и тапнуть на него".

Чтобы решить эти проблемы, мы создадим слой абстракций.

== Базовый класс для экранов

Чтобы избавиться от дублирования свойства `app` и инициализатора, мы создадим базовый класс `BaseScreen`, от которого будут наследоваться все наши Page Objects.

Создайте новый Swift файл `BaseScreen.swift`:

[source, swift]
--
// BaseScreen.swift
import XCTest

class BaseScreen {
    let app: XCUIApplication

    init(app: XCUIApplication) {
        self.app = app
    }
}
--

Теперь мы можем упростить наши Page Objects, унаследовав их от `BaseScreen`.

*Пример рефакторинга `LoginPage`*:

[source, swift]
--
// LoginPage.swift
import XCTest

class LoginPage: BaseScreen { // Наследуемся от BaseScreen

    // Свойство `app` и `init` теперь не нужны, они унаследованы

    // Elements
    private lazy var usernameTextField = app.textFields.element(boundBy: 0)
    private lazy var passwordTextField = app.secureTextFields.element(boundBy: 0)
    private lazy var loginButton = app.buttons["Login"]

    // ... остальной код ...
}
--

Проделайте то же самое для `MenuPage` и `ProductsPage`.

== Централизация идентификаторов

Чтобы избавиться от "магических строк", создадим единое место для хранения всех идентификаторов. Для этого отлично подходит перечисление (`enum`).

Создайте новый файл `AppElement.swift`:

[source, swift]
--
// AppElement.swift
import Foundation

enum AppElement: String {
    // Menu
    case moreTabItem = "More-tab-item"
    case loginMenuItem = "Login Button"

    // Login
    case loginButton = "Login"

    // Products
    case productsHeader = "Products"
}
--

Теперь мы можем использовать этот `enum` для доступа к элементам, что делает код более безопасным и читаемым. Компилятор не позволит нам ошибиться в имени.

*Пример рефакторинга `LoginPage`*:

[source, swift]
--
// LoginPage.swift
class LoginPage: BaseScreen {
    // ...
    // Elements
    private lazy var usernameTextField = app.textFields.element(boundBy: 0)
    private lazy var passwordTextField = app.secureTextFields.element(boundBy: 0)
    private lazy var loginButton = app.buttons[AppElement.loginButton.rawValue] // Используем enum
    // ...
}
--

== Расширения для `XCUIElement`

Часто простого `.tap()` недостаточно. Элемент может еще не появиться на экране, и тест упадет. Хорошей практикой является ожидание появления элемента перед взаимодействием. Чтобы не писать код ожидания каждый раз, мы можем создать удобные методы-обертки с помощью расширений (`extension`).

Создайте новый файл `XCUIElement+Extensions.swift`:

[source, swift]
--
// XCUIElement+Extensions.swift
import XCTest

extension XCUIElement {

    /// Ожидает, пока элемент не станет видимым и доступным для нажатия.
    /// Этот метод более надежен, чем `waitForExistence`, так как проверяет свойство `isHittable`.
    /// - Parameter timeout: Время ожидания в секундах. По умолчанию 5.
    /// - Returns: `true`, если элемент стал доступен для взаимодействия.
    @discardableResult
    func waitUntilVisible(timeout: TimeInterval = 5) -> Bool {
        let hittablePredicate = NSPredicate(format: "isHittable == true")
        let expectation = XCTNSPredicateExpectation(predicate: hittablePredicate, object: self)
        return XCTWaiter.wait(for: [expectation], timeout: timeout) == .completed
    }

    /// Ожидает появления элемента в течение `timeout` секунд, а затем нажимает на него.
    /// - Parameter timeout: Время ожидания в секундах. По умолчанию 5.
    func waitAndTap(timeout: TimeInterval = 5) {
        // Используем наш новый, более надежный метод ожидания
        XCTAssertTrue(self.waitUntilVisible(timeout: timeout), "Элемент \(self) не стал видимым и доступным для нажатия.")
        self.tap()
    }

    /// Очищает текстовое поле и вводит новый текст.
    /// - Parameter text: Текст для ввода.
    func clearAndTypeText(_ text: String) {
        self.tap()
        // Если в поле уже есть текст, удаляем его
        if let stringValue = self.value as? String, !stringValue.isEmpty {
            // Нажимаем кнопку "Очистить текст" (крестик)
            if self.buttons["Clear text"].exists {
                self.buttons["Clear text"].tap()
            } else {
                // Если крестика нет, удаляем посимвольно
                let deleteString = String(repeating: XCUIKeyboardKey.delete.rawValue, count: stringValue.count)
                self.typeText(deleteString)
            }
        }
        self.typeText(text)
    }
}
--

Теперь наши действия в Page Objects станут еще лаконичнее.

*Пример рефакторинга `LoginPage`*:

[source, swift]
--
// LoginPage.swift
class LoginPage: BaseScreen {
    // ...
    // Actions
    @discardableResult
    func login(user: String, pass: String) -> ProductsPage {
        usernameTextField.clearAndTypeText(user) // Используем новый метод
        passwordTextField.clearAndTypeText(pass) // Используем новый метод

        // Баг: клавиатура не убирается.
        // app.keyboards.buttons["Return"].tap()

        loginButton.waitAndTap() // Используем новый метод

        return ProductsPage(app: app)
    }
}
--

== Паттерн "Робот" как Фабрика Экранов

Мы создали отличные абстракции, но в тестах все еще остался один повторяющийся элемент: ручное создание экземпляров Page Object'ов (`let menuPage = MenuPage(app: app)`). По мере роста количества тестов это может стать утомительным. Существует элегантный гибридный подход, который решает эту проблему, — паттерн **"Робот-Контейнер"** или **"Робот как Фабрика Экранов"**.

Идея проста:

1.  Создается единый класс-фасад `AppRobot`, который является точкой входа для всех тестов.
2.  Этот робот не выполняет действия сам, а хранит "ленивые" (`lazy`) экземпляры всех наших Page Object'ов.
3.  Тест обращается к роботу, чтобы получить нужный экран, а затем вызывает методы этого экрана.

=== 1. Создание `AppRobot`

Создадим новый файл `AppRobot.swift`.

[source, swift]
--
// AppRobot.swift
import XCTest

class AppRobot {
    private let app: XCUIApplication

    // "Ленивые" свойства для каждого экрана.
    // Экземпляр создается только при первом обращении.
    lazy var menuScreen = MenuPage(app: app)
    lazy var loginScreen = LoginPage(app: app)
    lazy var productsScreen = ProductsPage(app: app)

    init(app: XCUIApplication) {
        self.app = app
        // Можно сразу запускать приложение при инициализации робота
        app.launch()
    }
}
--

=== 2. Обновленный тест с использованием Робота

Теперь наш тест становится еще чище. Нам не нужно создавать экземпляры страниц вручную — мы просто берем их у робота.

[source, swift]
--
// LoginUiTests.swift
@MainActor
func testSuccessfulLoginWithRobot() {
    // Arrange
    let robot = AppRobot(app: app)

    // Act
    robot.menuScreen.openLoginScreen()
    robot.loginScreen.login(user: "bob@example.com", pass: "10203040")

    // Assert
    XCTAssertTrue(robot.productsScreen.isProductsHeaderVisible(), "Не удалось перейти на экран продуктов после логина")
}
--

Этот подход сочетает в себе читаемость тестов от паттерна "Робот" и масштабируемость от "Page Object Model", являясь мощной архитектурой для тестового фреймворка.

== Что дальше?

Мы создали прочный фундамент для нашего фреймворка. Код стал более структурированным, читаемым и легким в поддержке. Однако, сами проверки в тестах все еще можно сделать более выразительными.

В следующем уроке мы научимся создавать собственные, кастомные ассерты, такие как `XCTAssertVisible`, чтобы сделать наши тесты еще чище и понятнее.
