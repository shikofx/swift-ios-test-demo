= Написание новых тестов с использованием абстракций

В предыдущем уроке мы создали базовые классы, централизовали идентификаторы и написали удобные расширения. Теперь давайте посмотрим, как эти улучшения помогают нам в написании новых тестов.

Мы напишем негативный тест, который проверяет поведение приложения при вводе неверных учетных данных.

== Тестовый сценарий: Неудачный логин

1.  Открыть экран логина.
2.  Ввести невалидное имя пользователя (например, `wrong_user`).
3.  Ввести невалидный пароль (например, `wrong_pass`).
4.  Нажать на кнопку "Login".
5.  Убедиться, что на экране появилось сообщение об ошибке.

== 1. Обновление `AppElement`

Первым делом, нам нужно добавить идентификатор для сообщения об ошибке в наш `enum`. С помощью `Accessibility Inspector` или `po app` мы выяснили, что у сообщения об ошибке на экране логина есть идентификатор `generic-error-message`.

Добавим его в `AppElement.swift`:

[source, swift]
--
// AppElement.swift
enum AppElement: String {
    // ... существующие кейсы

    // Login
    case loginButton = "Login"
    case genericErrorMessage = "generic-error-message" // <-- Наш новый элемент

    // ...
}
--

== 2. Расширение `LoginPage`

Теперь добавим в наш `LoginPage` элемент для сообщения об ошибке и метод для проверки его видимости и текста.

[source, swift]
--
// LoginPage.swift
class LoginPage: BaseScreen {
    // ...
    // Elements
    private lazy var usernameTextField = app.textFields.element(boundBy: 0)
    private lazy var passwordTextField = app.secureTextFields.element(boundBy: 0)
    private lazy var loginButton = app.buttons[AppElement.loginButton.rawValue]
    private lazy var errorMessage = app.staticTexts[AppElement.genericErrorMessage.rawValue] // <-- Добавили элемент

    // ...

    // Verifications
    /// Проверяет, что сообщение об ошибке видимо
    func isErrorMessageVisible() -> Bool {
        return errorMessage.waitForExistence(timeout: 5)
    }

    /// Возвращает текст сообщения об ошибке
    func getErrorMessageText() -> String {
        return errorMessage.label
    }
}
--

Обратите внимание, мы не меняли существующий метод `login()`, так как он описывает *успешный* сценарий, который приводит к переходу на другой экран. Для негативного теста мы будем вызывать действия по отдельности.

== 3. Написание нового теста

Теперь мы готовы добавить новый тестовый метод в `LoginUiTests.swift`. Посмотрите, каким лаконичным и читаемым он получился благодаря нашей подготовке.

[source, swift]
--
// LoginUiTests.swift

// ... существующий тест testSuccessfulLogin() ...

@MainActor
func testInvalidLogin() {
    // Arrange: Подготовка
    let menuPage = MenuPage(app: app)
    let loginPage = menuPage.openLoginScreen()

    // Act: Действие
    loginPage.login(user: "wrong_user", pass: "wrong_pass")

    // Assert: Проверка
    XCTAssertTrue(loginPage.isErrorMessageVisible(), "Сообщение об ошибке не появилось на экране.")
    XCTAssertEqual(loginPage.getErrorMessageText(), "Provided credentials do not match any user in this service.", "Текст сообщения об ошибке неверный.")
}
--

Вот и все! Мы написали новый, полностью рабочий UI-тест, добавив всего несколько строк кода. Нам не пришлось заново искать элементы или думать, как с ними взаимодействовать. Вся эта логика уже была готова в наших Page Objects и расширениях.

== Что дальше?

Наши тесты становятся все лучше, но у нас все еще есть "магические" данные прямо в коде тестов (`"wrong_user"`, `"wrong_pass"`). В следующем уроке мы создадим вспомогательные классы (хелперы) для управления тестовыми данными, чтобы сделать наши тесты еще более гибкими и поддерживаемыми.
