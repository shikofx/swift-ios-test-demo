= Введение в API-хелперы для подготовки состояния приложения

Наши UI-тесты становятся все более сложными. Но у них есть одна фундаментальная проблема: они зависят от состояния, оставшегося от предыдущего запуска. Если один тест добавит товар в корзину, следующий тест начнется с непустой корзиной, что может привести к его падению.

**Каждый UI-тест должен начинаться с чистого, предсказуемого состояния.**

Подготавливать состояние через UI (например, логиниться и добавлять товары в корзину перед каждым тестом) — очень медленно и ненадежно. В этом уроке мы рассмотрим два подхода для решения этой проблемы.

== 1. Идеальный подход: API-хелперы

В большинстве реальных приложений есть серверная часть (backend) с API. Идеальный способ подготовить состояние — это сделать прямые API-запросы к серверу перед запуском теста.

*   **Пример:** Чтобы протестировать корзину с 5 товарами, вместо того чтобы 5 раз кликать по UI, мы можем сделать один API-запрос, который добавит эти товары для нашего тестового пользователя.

Это **значительно** быстрее и стабильнее, чем эмуляция действий через UI.

=== Как бы это выглядело в коде?

Мы бы создали простой API-клиент, который умеет выполнять нужные нам запросы.

[source, swift]
--
// APIClient.swift (Теоретический пример)

import Foundation

class APIClient {
    private let baseURL = URL(string: "https://api.myapp.com/v1/")!

    /// Сбрасывает состояние пользователя на сервере
    func resetUserState(for user: TestUser) async throws {
        // Код для выполнения сетевого запроса на сброс состояния
        // let request = URLRequest(...)
        // let (data, _) = try await URLSession.shared.data(for: request)
        print("Состояние для пользователя \(user.username) сброшено через API.")
    }

    /// Добавляет продукт в корзину через API
    func addProductToCart(_ productId: String, for user: TestUser) async throws {
        // Код для выполнения сетевого запроса на добавление товара
        print("Продукт \(productId) добавлен в корзину через API.")
    }
}
--

Затем в `setUp` нашего теста мы бы вызывали эти методы:

[source, swift]
--
// BaseUITest.swift (Теоретический пример)

override func setUp() {
    super.setUp()
    Task {
        // Перед каждым тестом сбрасываем состояние пользователя
        try await apiClient.resetUserState(for: .standard)
    }
    // ...
}
--

[IMPORTANT]
====
Наше демо-приложение `SDET Demo App` является полностью клиентским и **не имеет backend API**. Поэтому мы не можем реализовать этот подход на практике, но знание о нем абсолютно необходимо для работы в реальных проектах.
====

== 2. Прагматичный подход: Аргументы запуска

Что делать, если API нет? Мы можем заставить само приложение сбросить свое состояние при запуске. Для этого используются **аргументы запуска** (`launchArguments`), с которыми мы уже познакомились в первом уроке.

Идея в следующем:
1.  Мы передаем приложению при запуске специальный флаг, например, `--reset`.
2.  Основной код приложения проверяет наличие этого флага.
3.  Если флаг найден, приложение выполняет внутреннюю логику для очистки своего состояния (например, удаляет данные из `UserDefaults`, очищает базу данных).

В нашем демо-приложении уже есть такая логика, которая срабатывает при нажатии на кнопку "Reset App State" в меню. Нам нужно научиться вызывать ее программно.

=== Реализация

==== Шаг 1: Добавляем базовый тестовый класс

Чтобы не дублировать код настройки в каждом тестовом классе, создадим `BaseUITest`.

Создайте новый файл `BaseUITest.swift`:

[source, swift]
--
// BaseUITest.swift

import XCTest

class BaseUITest: XCTestCase {
    var app: XCUIApplication!

    override func setUp() {
        super.setUp()
        continueAfterFailure = false

        app = XCUIApplication()

        // Добавляем аргумент для сброса состояния
        app.launchArguments.append("--reset")

        app.launch()
    }
}
--

==== Шаг 2: Обновляем существующие тесты

Теперь изменим `LoginUiTests`, чтобы он наследовался от нашего нового базового класса.

[source, swift]
--
// LoginUiTests.swift

import XCTest

final class LoginUiTests: BaseUITest { // <-- Наследуемся от BaseUITest

    // Метод setUp() больше не нужен, вся логика в базовом классе

    @MainActor
    func testSuccessfulLogin() {
        // ... код теста остается без изменений
    }

    @MainActor
    func testInvalidLogin() {
        // ... код теста остается без изменений
    }
}
--

Теперь перед каждым запуском любого теста, унаследованного от `BaseUITest`, приложение будет получать флаг `--reset` и (после добавления соответствующего кода в само приложение) будет запускаться в чистом состоянии.
