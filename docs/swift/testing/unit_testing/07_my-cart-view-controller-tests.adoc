== Теория

На этом уроке мы перейдем от теории к практике. Мы напишем тесты для `MyCartViewController`, который отвечает за отображение товаров в корзине, управление их количеством и расчет итоговой стоимости.

=== Подготовка к тестированию: `setUp` и `tearDown`

Ключевая проблема при тестировании `UIViewController` — его зависимость от глобального состояния, в нашем случае — синглтона `Engine.sharedInstance`. Если тесты будут изменять один и тот же глобальный объект, они станут зависимы друг от друга. Один тест сможет повлиять на результат другого.

Чтобы избежать этого, мы будем использовать методы `setUp()` и `tearDown()`:

*   `setUp()`: Вызывается *перед каждым* тестовым методом. Здесь мы создаем "чистый" экземпляр `Engine` и подменяем им глобальный синглтон. Это гарантирует, что каждый тест начинается с одинаковых, предсказуемых условий.
*   `tearDown()`: Вызывается *после каждого* тестового метода. Здесь мы очищаем ресурсы, чтобы не оставлять "мусора" после себя.

[source,swift]
----
class MyCartViewControllerTests: XCTestCase {

    var sut: MyCartViewController!
    var engine: Engine!

    override func setUp() {
        super.setUp()
        // Given: Создаем чистый экземпляр Engine для каждого теста
        engine = Engine()
        Engine.sharedInstance = engine

        // Given: Загружаем контроллер из Storyboard
        let storyboard = UIStoryboard(name: "TabBar", bundle: nil)
        sut = storyboard.instantiateViewController(withIdentifier: "MyCartViewController") as? MyCartViewController
        
        // Given: Загружаем view, чтобы IBOutlets были инициализированы
        sut.loadViewIfNeeded()
    }

    override func tearDown() {
        sut = nil
        engine = nil
        super.tearDown()
    }
}
----

==== Что означает `!` (неявно извлекаемый опционал)?

Знак `!` в конце типа (`MyCartViewController!`) объявляет переменную как **неявно извлекаемый опционал** (Implicitly Unwrapped Optional). Это ключевая особенность Swift, связанная с безопасностью.

Она говорит компилятору:
____
Я, разработчик, обещаю, что эта переменная *никогда не будет `nil`* в тот момент, когда я попытаюсь ее использовать. Поэтому, пожалуйста, не заставляй меня проверять ее на `nil` каждый раз. Просто автоматически извлекай значение за меня.
____

В нашем коде это работает так:
. Переменная `sut` объявляется, но в этот момент она равна `nil`.
. В методе `setUp()`, который выполняется *перед каждым тестом*, мы создаем экземпляр контроллера и присваиваем его `sut`.
. Таким образом, к моменту запуска любого теста (`test...()`) мы гарантируем, что `sut` уже инициализирован.

Этот подход позволяет писать более чистый и читаемый тестовый код, так как нам не нужно постоянно использовать `?` или `!` при обращении к `sut`.

[WARNING]
====
Если вы нарушите свое обещание и попытаетесь использовать `sut`, когда он будет `nil` (например, если забудете инициализировать его в `setUp()`), ваше приложение **немедленно упадет с ошибкой**. В контексте тестов это даже хорошо, потому что вы сразу видите, что тест настроен неправильно.
====

`sut` (System Under Test) — это общепринятое название для объекта, который мы тестируем.

==== Загрузка контроллера из Storyboard

Давайте разберем, как мы получаем наш `sut` (System Under Test):

[source,swift]
----
let storyboard = UIStoryboard(name: "TabBar", bundle: nil)
sut = storyboard.instantiateViewController(withIdentifier: "MyCartViewController") as? MyCartViewController
----

1.  **`let storyboard = UIStoryboard(name: "TabBar", bundle: nil)`**
+
Эта строка находит в проекте файл визуального интерфейса с именем `TabBar.storyboard` и загружает его в память как объект `storyboard`. Параметр `bundle: nil` означает, что поиск будет производиться в основном пакете приложения, где обычно и лежат все ресурсы.

2.  **`sut = storyboard.instantiateViewController(...)`**
+
Эта строка обращается к загруженному storyboard и просит его создать реальный экземпляр (`instantiate`) вью-контроллера. Чтобы найти нужный, мы используем его уникальный идентификатор — `MyCartViewController`, который задается в Xcode в Identity Inspector.

3.  **`as? MyCartViewController`**
+
Так как `instantiateViewController` возвращает общий тип `UIViewController`, мы должны привести его к нашему конкретному классу `MyCartViewController`, чтобы получить доступ к его свойствам и методам. `as?` — это безопасное приведение типа, которое вернет `nil`, если что-то пойдет не так, и не приведет к падению теста.

=== Структурирование тестов с помощью `XCTContext.runActivity`

В `XCTest` нет прямого аналога аннотации `@DisplayName`, как в других фреймворках. Вместо этого мы можем создать свой собственный DSL (предметно-ориентированный язык) для тестов, используя `XCTContext.runActivity`.

Это позволяет нам писать тесты в очень читаемом BDD-стиле (Behavior-Driven Development), используя структуру **Given-When-Then**.

Для этого мы создадим `extension` для `XCTest`:

[source,swift]
----
extension XCTest {
    func given(_ desc: String = "", _block block: @MainActor (any XCTActivity) -> Void) {
        XCTContext.runActivity(named: "Given: \(desc)", block: block)
    }
    
    func when(_ desc: String = "", _block block: @MainActor (any XCTActivity) -> Void) {
        XCTContext.runActivity(named: "When: \(desc)", block: block)
    }
    
    func then(_ desc: String = "", _block block: @MainActor (any XCTActivity) -> Void) {
        XCTContext.runActivity(named: "Then: \(desc)", block: block)
    }
}
----

Теперь наши тесты становятся декларативными и очень легко читаются:

[source,swift]
----
func test_calculateTotalPrice_when_cartIsEmpty_then_zero() {
    given("в корзине нет товаров") { _ in
        engine.cartList = []
    }
    
    when("рассчитывается общая стоимость") { _ in
        sut.calculateTotalPrice()
    }
    
    then("итоговая стоимость должна быть равна нулю") { _ in
        XCTAssertEqual(engine.totalPrice, 0.00)
        XCTAssertEqual(sut.totalPriceLbl.text, "$0.00")
    }
}
----

==== Что означает `_ in`?

Эта конструкция является частью синтаксиса **замыканий** (closures) в Swift. Давайте разберем ее на части:

*   **`{ ... }`**: Фигурные скобки определяют тело замыкания — это анонимный блок кода, который мы передаем в качестве аргумента в функцию `given`.
*   **`_` (подчеркивание)**: В Swift это специальный символ, который означает "я знаю, что здесь есть значение, но оно мне не нужно, и я собираюсь его проигнорировать".
*   **`in`**: Это ключевое слово, которое отделяет список параметров замыкания от его исполняемого кода (тела).

Вместе `_ in` говорит компилятору:
____
Я создаю блок кода (замыкание). Я знаю, что функция `given` передаст мне сюда один параметр (в данном случае, объект `XCTActivity`), но внутри этого блока кода он мне не понадобится, поэтому я явно его игнорирую.
____

Если бы нам *нужен* был этот параметр, мы бы дали ему имя, например:

[source,swift]
----
given("в корзине нет товаров") { activity in
    // Здесь мы могли бы использовать 'activity' для каких-то действий
    engine.cartList = []
}
----

====
*Имя функции (`test...`):* Кратко описывает сценарий в формате `test_ЧтоДелаем_ПриКакихУсловиях_КакойРезультат`.
*Имя активности (`named: ...`):* Подробно и на естественном языке описывает, что происходит на каждом шаге (Given, When, Then).
====

=== 1. Расчет общей стоимости (`calculateTotalPrice`)

==== UC-MCV-001: Расчет для пустой корзины

*Тест:* Проверяем, что для пустой корзины итоговая стоимость равна нулю.

[source,swift]
----
func test_calculateTotalPrice_when_cartIsEmpty_then_totalIsZero() {
    given("в корзине нет товаров") { _ in
        engine.cartList = []
    }

    when("рассчитывается общая стоимость") { _ in
        sut.calculateTotalPrice()
    }

    then("итоговая стоимость должна быть равна нулю") { _ in
        XCTAssertEqual(engine.totalPrice, 0.0)
        XCTAssertEqual(sut.totalPriceLbl.text, "$0.00")
    }
}
----


==== UC-MCV-002 & UC-MCV-003: Расчет для одного и нескольких товаров

*Тест:* Проверяем корректность расчета для одного товара с количеством > 1 и для нескольких разных товаров.

[source,swift]
----
func testCalculateTotalPrice_WithMultipleItems_ShouldBeCorrect() {
    given("в корзине есть несколько товаров") { _ in
        let item1: NSMutableDictionary = ["ProductPrice": "15.99", "ProductQuantity": 2]
        let item2: NSMutableDictionary = ["ProductPrice": "29.99", "ProductQuantity": 1]
        engine.cartList = [item1, item2]
    }

    when("рассчитывается общая стоимость") { _ in
        sut.calculateTotalPrice()
    }

    then("итоговая стоимость должна быть корректной") { _ in
        let expectedTotal = 15.99 * 2 + 29.99
        XCTAssertEqual(engine.totalPrice, expectedTotal)
        XCTAssertEqual(sut.totalPriceLbl.text, "$\(String(format: "%.2f", expectedTotal))")
    }
}
----

=== 2. Управление товарами в корзине

==== UC-MCV-004: Увеличение количества товара

*Тест:* Проверяем, что нажатие на "+" увеличивает количество товара и общий счетчик.

[source,swift]
----
func testAddButton_IncreasesQuantityAndCartCount() {
    given("в корзине есть товар с количеством 1") { _ in
        let item: NSMutableDictionary = ["ProductPrice": "10.00", "ProductQuantity": 1]
        engine.cartList = [item]
        engine.cartCount = 1
    }

    when("нажимается кнопка '+' для этого товара") { _ in
        let mockButton = UIButton()
        mockButton.tag = 0 // Индекс товара
        sut.addButton(mockButton)
    }

    then("количество товара и общий счетчик должны увеличиться") { _ in
        XCTAssertEqual(engine.cartList[0]["ProductQuantity"] as? Int, 2)
        XCTAssertEqual(engine.cartCount, 2)
    }
}
----

==== Как работает "мок" кнопки?

Давайте разберем, как работает этот "мок" и почему он используется в тесте.

[source,swift]
----
// 1. Создаем "поддельный" объект кнопки
let mockButton = UIButton()

// 2. Настраиваем единственное важное для нас свойство
mockButton.tag = 0

// 3. Вызываем тестируемый метод, передавая ему наш объект
sut.addButton(mockButton)
----

1.  **`let mockButton = UIButton()`**: Здесь мы создаем самый обычный, реальный экземпляр класса `UIButton`. В данном контексте слово "мок" (mock) используется не в строгом смысле (как объект, созданный специальной библиотекой для мокирования), а скорее как **"заглушка"** или **"тестовый двойник" (Test Double)**. Его цель — имитировать объект, который в реальном приложении создается и управляется UI, но для unit-теста нам не нужен весь UI.

2.  **`mockButton.tag = 0`**: Это ключевой шаг. Мы смотрим на тестируемый метод `addButton(_ sender: UIButton)` в файле `MyCartViewController.swift` и видим, что внутри он использует свойство `sender.tag` для получения индекса товара в массиве `cartList`.
+
[source,swift]
----
// MyCartViewController.swift
@objc func addButton(_ sender: UIButton) {
    // Метод использует .tag, чтобы найти нужный товар
    let productFound = Engine.sharedInstance.cartList[sender.tag]
    // ... остальная логика
}
----
+
В нашем тесте мы устанавливаем `tag = 0`, чтобы сымитировать нажатие на кнопку "+" для **самого первого** товара в корзине (который находится по индексу 0).

3.  **`sut.addButton(mockButton)`**: Здесь мы напрямую вызываем метод `addButton` у нашего объекта `sut` (System Under Test, т.е. `MyCartViewController`). Мы передаем ему нашу "заглушку" `mockButton` в качестве параметра `sender`. Метод получает этот объект, читает из него `tag` (который равен 0) и выполняет свою бизнес-логику для товара с индексом 0.

===== Зачем это нужно?

Основная цель unit-теста — проверить **бизнес-логику** одного конкретного метода в **изоляции** от остальной системы.

*   **Изоляция от UI**: Нам не нужно загружать всю таблицу, создавать ячейки, симулировать реальное нажатие пальцем на экран. Это было бы долго, сложно и относилось бы уже к UI-тестам.
*   **Скорость**: Создание простого объекта `UIButton` и вызов метода — это очень быстрая операция, что критически важно для unit-тестов.
*   **Простота**: Мы создаем только то, что необходимо для работы метода. Методу `addButton` нужен объект типа `UIButton`, у которого есть свойство `tag`. Мы ему это и предоставляем, больше ничего не требуется.

Таким образом, этот подход позволяет нам протестировать логику увеличения количества товара, не вовлекая сложный и медленный пользовательский интерфейс.

==== UC-MCV-005: Уменьшение количества товара (когда > 1)

*Тест:* Проверяем, что нажатие на "-" уменьшает количество товара, но не удаляет его, если количество было больше 1.

[source,swift]
----
func testSubtractButton_DecreasesQuantityAndCartCount() {
    given("в корзине есть товар с количеством > 1") { _ in
        let item: NSMutableDictionary = ["ProductPrice": "10.00", "ProductQuantity": 3]
        engine.cartList = [item]
        engine.cartCount = 3
    }

    when("нажимается кнопка '-' для этого товара") { _ in
        let mockButton = UIButton()
        mockButton.tag = 0
        sut.subtractButton(mockButton)
    }

    then("количество товара и общий счетчик должны уменьшиться") { _ in
        XCTAssertEqual(engine.cartList[0]["ProductQuantity"] as? Int, 2)
        XCTAssertEqual(engine.cartCount, 2)
        XCTAssertEqual(engine.cartList.count, 1, "Товар не должен быть удален")
    }
}
----
