== Теория

На этом уроке мы напишем тесты для `CatalogViewController`. Его основная задача — отображать список товаров и предоставлять пользователю возможность их сортировки по имени и цене.

=== Подготовка к тестированию (`setUp`)

Как и в предыдущем уроке, мы используем `setUp()` для подготовки чистого окружения для каждого теста.

[source,swift]
----
final class CatalogViewControllerTests: XCTestCase {

    var engine: Engine!
    var controller: CatalogViewController!

    override func setUp() {
        // Given: Создаем чистый экземпляр Engine
        engine = Engine()
        Engine.sharedInstance = engine

        // Given: Загружаем контроллер из Storyboard
        let storyboard = UIStoryboard(name: "TabBar", bundle: nil)
        controller = storyboard.instantiateViewController(withIdentifier: "CatalogViewController") as? CatalogViewController
        
        // Given: Загружаем view, чтобы IBOutlets (кнопки, лейблы) были инициализированы
        controller.loadViewIfNeeded()
    }
    // ...
}
----

Ключевой момент здесь — `controller.loadViewIfNeeded()`. Этот вызов заставляет контроллер загрузить свой `view` и все связанные с ним UI-элементы (`@IBOutlet`). Без этого любая попытка обратиться к кнопке, например `controller.nameAscendingBtn`, привела бы к падению теста, так как кнопка была бы `nil`.

==== Это все еще Unit-тест?

Строго говоря, как только мы вызываем `controller.loadViewIfNeeded()`, тест перестает быть **"чистым" unit-тестом** и становится скорее быстрым **интеграционным тестом**.

*   **Unit-тест** проверяет один компонент в полной изоляции.
*   **Интеграционный тест** проверяет, как несколько компонентов работают вместе.

Вызывая `loadViewIfNeeded()`, мы заставляем наш код взаимодействовать с фреймворком `UIKit` (загрузка view, инициализация `@IBOutlet`, вызов `viewDidLoad`).

Однако в контексте iOS-разработки это является общепринятой и прагматичной практикой. Такие тесты остаются очень быстрыми и не требуют запуска симулятора, поэтому их часто относят к общей категории "unit-тестов", чтобы отделить от медленных UI-тестов.

=== Симуляция нажатия кнопки

В Unit-тестах у нас нет реального UI, поэтому мы не можем "нажать" на кнопку. Вместо этого мы **симулируем нажатие**, напрямую вызывая метод-обработчик (`@IBAction`), который привязан к этой кнопке.

[source,swift]
----
when("происходит сортировка по имени") { _ in
    // Симулируем нажатие, вызывая IBAction и передавая ему саму кнопку
    controller.nameAscendingButton(controller.nameAscendingBtn)
}
----

*   `controller.nameAscendingButton(...)` — это вызов метода `@IBAction`.
*   `controller.nameAscendingBtn` — это сама кнопка (`UIButton`), которую мы передаем в качестве аргумента `sender`.

Этот подход позволяет нам протестировать логику, которая выполняется при нажатии, в полной изоляции от UI.

== Практика: Пишем тесты для сортировки

Мы напишем тесты для всех четырех сценариев сортировки, описанных в `CatalogViewController.adoc`.

=== UC-CV-001: Сортировка по имени (A-Z)

*Тест:* Проверяем, что после вызова `nameAscendingButton()` товары отсортированы в алфавитном порядке.

[source,swift]
----
func test_sort_ByNameAscending() {
    given("несортированный список товаров") { _ in
        engine.productList = [
            ["ProductName": "Sauce Labs T-Shirt", "ProductPrice": "15.99"],
            ["ProductName": "Sauce Labs Backpack", "ProductPrice": "29.99"],
            ["ProductName": "Sauce Labs Onesie", "ProductPrice": "7.99"]
        ]
    }

    when("происходит сортировка по имени (A-Z)") { _ in
        controller.nameAscendingButton(controller.nameAscendingBtn)
    }

    then("список отсортирован по имени в алфавитном порядке") { _ in
        let expectedList: [NSMutableDictionary] = [
            ["ProductName": "Sauce Labs Backpack", "ProductPrice": "29.99"],
            ["ProductName": "Sauce Labs Onesie", "ProductPrice": "7.99"],
            ["ProductName": "Sauce Labs T-Shirt", "ProductPrice": "15.99"]
        ]
        XCTAssertEqual(engine.productList, expectedList)
    }
}
----
